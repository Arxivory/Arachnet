The Pipeline Mapped to Your Code
The PDF describes a 6-step pipeline. Here's exactly where each step lives in your architecture:
Step 1 — Ingress / MAC match
* Already handled: Interface.receivePacket() → device.onPacketReceived(packet, ingressInterface)
* Router.onPacketReceived needs to check if the destination MAC matches the ingress interface's MAC. If not, drop.
Step 2 — Decapsulation
* PacketBuilder.js strips the Ethernet header and hands up the raw IP packet. You need a defined packet schema here — this is important.
Step 3 — Routing Lookup (LPM)
* RoutingTable.js — this is the core of routing. Longest Prefix Match against the table. Returns { nextHop, egressInterface }.
Step 4 — TTL Handling
* Inside Router.onPacketReceived — decrement, check zero, trigger ICMPHandler.timeExceeded().
Step 5 — Next-Hop Resolution (ARP)
* ARPCache.js — check cache first. On miss, generate an ARP request event, queue the original packet, resume on reply.
Step 6 — Encapsulation + Forward
* PacketBuilder.js wraps the IP packet in a new Ethernet frame with resolved MACs, then calls egressInterface's port's link's transmitPacket().
________________


The Most Critical Design Decision: The Packet Schema
Before writing any routing logic, you need to agree on what a packet object looks like. Right now transmitPacket(packet, fromPort) passes an opaque packet object. You need to define it. I'd suggest two layers:
js
// Ethernet Frame (Layer 2)
{
  srcMAC: '00:1A:2B:3C:4D:5E',
  dstMAC: 'FF:FF:FF:FF:FF:FF',
  vlanTag: null,          // or { id: 10, priority: 0 }
  etherType: 0x0800,      // 0x0800 = IPv4, 0x0806 = ARP
  payload: <IPPacket>
}


// IP Packet (Layer 3)
{
  srcIP:    '192.168.1.10',
  dstIP:    '10.0.0.5',
  ttl:      64,
  protocol: 'icmp',       // 'tcp', 'udp', 'icmp'
  payload:  <any>
}
This is the backbone everything else depends on. Get this wrong and you'll be refactoring across every file.

The SimulationBus — Why It Matters
The PDF specifically says avoid continuous simulation, use discrete events. This is the right call and it maps perfectly to your existing setTimeout-based latency in Link.transmitPacket(). But right now that's ad-hoc. You want a proper event queue so you can:
* Replay simulations
* Pause/step through packet hops
* Visualize packet travel in your 3D canvas
* Handle ARP "pending" queues without race conditions
SimulationBus.js would be a priority queue of { time, type, handler } events — the single clock that drives everything.

Recommended Build Order
1. Packet schema — define it, document it, commit it. Everything depends on this.
2. RoutingTable.js — LPM, static routes, addRoute / lookup. Testable in isolation.
3. ARPCache.js — cache, request/reply simulation. Also testable alone.
4. Router.js — wire the full pipeline using the above two.
5. ICMPHandler.js — ping and TTL exceeded, makes testing the pipeline visible.
6. SimulationBus.js — replace ad-hoc setTimeout calls, gives you the event model.
7. RIP — after static routing works end-to-end.
8. OSPF — last, it's complex and you won't need it to validate the core.

One Thing Worth Flagging
NetworkStore.addLink() extracts sourceId/targetId from linkData.sourcePort.id.split("::")[0] — but the store stores those as sourceId/targetId flat fields. When SimulationBus needs to traverse the graph (find what router is at the other end of a link), it'll need a clean graph traversal API. I'd suggest adding a getNeighbors(deviceId) method to NetworkStore early — it'll save you pain later.

The Problem With Extending Device
Since DeviceFactory constructs a base Device instance directly:
js
const device = new Device({ type: catalog.family, ... });
You can't just do class Router extends Device and expect DeviceFactory to produce it — the factory always returns a plain Device. You'd have to either:
* Option A — Make DeviceFactory aware of subtypes (messy, couples factory to routing logic)
* Option B — Use a mixin/behavior pattern: Router.js attaches routing behavior onto an existing Device instance at runtime
* Option C — Add a DeviceFactory.createRouter() specialized path that returns a Router extends Device instance
________________


My Recommendation: Option B — Behavior Attachment
This fits your architecture best because:
* DeviceFactory stays clean, no changes needed
* NetworkStore doesn't care what type the device is
* Routing logic is opt-in, only activated when device.type === 'router'
* Matches how Cisco IOS actually works — you enable routing features on a device, they're not baked into the hardware class
The pattern would look like this:
js
// Router.js — not a class, a behavior installer
export function installRouterBehavior(device) {
  device.routingTable = new RoutingTable(device);
  device.arpCache     = new ARPCache(device);
  device.icmp         = new ICMPHandler(device);


  // Override the stub from Device.js
  device.onPacketReceived = function(packet, ingressInterface) {
    RouterPipeline.process(packet, ingressInterface, device);
  };


  return device;
}
Then wherever you create a device (probably in NetworkStore.addDevice or wherever devices are placed on canvas):
js
if (device.type === 'router') {
  installRouterBehavior(device);
}
